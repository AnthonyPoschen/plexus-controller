# Architecture

This document captures the runtime architecture for Plexus game servers. It is the controller-side companion to the backend repository's `docs/game-deployment.md` and the disk proxy / editor pod implementation plan.

## Core Model

Plexus treats the backend database as the product and entitlement source of truth. Kubernetes (via this controller) is the runtime reconciliation surface.

- Backend owns: users, subscriptions, billing (Stripe), catalog, server entitlements, authorization, desired state.
- This controller owns: turning a `GameServer` CR into running pods, volumes, ConfigMaps, services, and short-lived editor pods.

The `GameServer` CR is the narrow contract between the two.

## Two-Layer File & Config Model

### 1. Config Layer (ConfigMaps) — Preferred for most settings

- The majority of editable server configuration (server.properties, config files, JSON, etc.) is modeled in `GameRuntimeProfile`.
- The controller renders these as ConfigMaps (or small templated ConfigMaps).
- Backend exposes tailored and allowlisted server-configuration APIs driven by
  the shared game-management schema.
- Customers may save changes only while runtime confirms the server is stopped.
- The next Start applies the saved configuration; there is no pending-restart
  editing state.
- This is safe, auditable, and the recommended path for the bulk of user-facing configuration.

### 2. Raw Disk / PVC Layer (Editor Pods) — For mods, world saves, bulk assets

- These files live on the PersistentVolumeClaim(s) attached to the game server.
- **Hard rule**: The main game server pod **must be stopped** before any direct mutation of raw disk content is allowed.
- When a managed save, backup, mod, or allowlisted advanced-config workflow needs
  raw-disk access:
  - Backend validates stopped/safe state (from GameServer CR status).
  - Controller (on demand) creates a short-lived **editor pod** that mounts the exact same PVC(s).
  - The editor pod runs a lightweight file server (HTTP, WebDAV, or a small web UI).
  - The backend exposes only the narrowly scoped operation authorized for that
    game workflow; customers never receive a general filesystem browser or
    arbitrary PVC path access.
  - All managed mutations go through the editor pod while the game pod is down.
  - On session end the controller tears down the editor pod.
- This prevents live filesystem races, open file handle problems, and accidental corruption.

### Bulk Archives (Worlds, Full Mod Packs)

- Large transfers use object storage (pre-signed URLs generated by the backend).
- User uploads/downloads directly to R2/S3.
- A separate "ingest" or "export" action (only while server is stopped) tells the controller to copy the archive safely between object storage and the PVC (using the editor pod context or a dedicated job).

## GameServer Custom Resource

The controller reconciles `GameServer` resources in the `plexus.gg/v1alpha1` API group.

Key responsibilities of the CR:

- Carry stable Server identity and ownership (server ID, owner user, and compute
  plan) independently from its optional selected setup/game.
- Express desired runtime configuration (desired power, optional selected setup,
  base compute plan, High performance entitlement, region, location, and a
  versioned structured game-configuration envelope).
- Surface rich status (phase, endpoint, conditions, observed generation, editor session state, etc.).

One stable CR represents one customer Server. The backend writes/updates desired
state; the controller makes it real and reports observed runtime state separately.
Game-specific configuration values use structured `runtime.RawExtension` inside
a versioned envelope, with sensitive values held in a referenced setup-scoped
Secret. Backend and controller consume the same controller-owned versioned game
management/secret schema library.

### Customer / Owner Lookup

The `spec.ownerUserID` field (from the backend's `app_users.id`) is the primary way to associate a `GameServer` with a customer.

For easy `kubectl` / observability queries, the controller should apply consistent labels on the `GameServer` and all child resources it creates:

- `plexus.gg/owner-user-id: <value>`
- `plexus.gg/server-id: <value>`
- `plexus.gg/game-id: <value>`

This allows commands like:
`kubectl get gameservers -l plexus.gg/owner-user-id=abc123`
`kubectl get pods,services,pvc -l plexus.gg/owner-user-id=abc123 -A`

See the `GameServer` spec for the `ownerUserID` field.

## Editor Pod Lifecycle (High Level)

1. User requests a managed save, backup, mod, or allowlisted advanced-config operation on a stopped server.
2. Backend validates ownership + stopped state.
3. Backend asks controller (via CR subresource, annotation, or separate request CR) for an editor session.
4. Controller creates a short-lived editor pod (same PVCs, appropriate security context and tools).
5. Controller exposes connection details (service, port, or short-lived token) in status or via an API response.
6. Backend authorizes and coordinates the narrow operation without exposing a general editor or arbitrary paths.
7. On explicit close or timeout: controller deletes the editor pod.

Editor pods are never long-lived. They exist only for the duration of the user's file management activity.

## Game Definitions (Controller-Owned) — Current Direction

Game-specific defaults, disk requirements, configuration templates, and runtime behavior live primarily **inside the controller** (see `internal/games/`).

When a `GameServer` is created or updated, the controller:

1. Looks up the `GameDefinition` for `spec.selectedSetup.gameID` when a setup is selected.
2. Applies game-owned defaults (image, environment, recommended disk, etc.).
3. Calculates final storage requirements at spin-up time:
   - `finalDisk = max(userRequest, computePlanStorage, gameDef.MinDiskGiB, gameDef.RecommendedDiskGiB)`
4. Decodes the selected setup's versioned structured configuration into the
   adapter's typed values, then creates PVCs, ConfigMaps, Services, and the main
   workload.
5. For raw disk paths, ensures they are only mutated via editor pods while the main server is stopped.

This keeps the `GameServer` CRD small and generic while giving each game rich, versioned, testable behavior inside the controller.

The backend catalog only needs high-level marketing + "recommended offering" data. Deep runtime knowledge stays in the controller.

See `internal/games/types.go` for the current structure (including `CalculateDiskSize` and `ConfigLayer` templates).

### Design Options Considered

- **Controller owns definitions** (chosen): All defaults + disk math live in Go code here. Strong consistency, easy to test and evolve per game. Disk sizing happens naturally during reconciliation/creation.
- **GameDefinition CRD** (alternative): A declarative `GameDefinition` CR per game, applied via GitOps. Very flexible but adds another CRD to manage.
- **Backend-owned profile synced to cluster**: Rich profiles live in the backend catalog and are pushed as ConfigMaps. Simpler contract for the backend UI, but splits ownership of runtime behavior.
- **Heavy CRD unions / per-game fields**: Rejected — leads to schema explosion and couples the API surface to individual games.

The current direction favors moving intelligence into the controller and keeping the `GameServer` CR lightweight.

## Status & Observability

The controller is responsible for keeping `GameServer.status` accurate so the backend dashboard can show customers a merged view:

- Entitlement state from SQLite (backend)
- Runtime health, endpoint, phase, and editor session state from the CR (controller)

High-cardinality metrics (CPU, memory, players, etc.) are expected to come from Prometheus or the Kubernetes metrics API, labeled consistently with `plexus.gg/server-id`.

## Safety & Invariants

- Never mutate raw disk while the main game pod is running.
- Never delete a PVC that still has billing/entitlement linkage in the backend.
- Editor pods must be cleaned up even if the client disconnects.
- All mutations that affect customer-visible state should be recorded in backend `server_actions` (via the backend API).

## Cross-Repo Boundaries

- Backend never creates Deployments, Pods, PVCs, or ConfigMaps directly for game servers.
- Controller never talks to Stripe, Clerk, or the billing/subscription tables.
- The narrow surface is the `GameServer` CR, its referenced setup-scoped Secret,
  and any small supporting resources for managed editor/archive operations.

See the backend repository for the product, catalog, and API side of the design.

## Deployment

The controller is deployed using the same FluxCD + Kustomize pattern as the backend.

- CRDs and controller manifests live under `kustomization/base/`
- Production overlays (image automation, secrets) live under `kustomization/overlays/prod/`
- CRDs are generated into `kustomization/base/crds/` via `make manifests`

This allows the controller to be managed by the same GitOps pipeline as the rest of the platform.
